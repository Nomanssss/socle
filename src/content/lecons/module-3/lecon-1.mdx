En plus du site, le template fabrique **une présentation par leçon**, et **un PDF par module**. C'est la seconde sortie évoquée au module 1.

## La commande

```bash
npm run slides
```

Elle produit, dans le dossier `slides/`, un PDF par leçon **et** un par module.

| Commande | Sortie | Chrome requis |
| --- | --- | --- |
| `npm run slides` | PDF | oui |
| `npm run slides:html` | HTML projetable | non |
| `npm run slides:pptx` | PowerPoint | oui |

Deux comportements à connaître :

- **tout** est retraité à chaque exécution, pas seulement ce que vous venez de modifier ;
- le dossier `slides/` est entièrement reconstruit. N'y écrivez jamais rien : la source est dans `src/content/`.

En PDF, tout régénérer prend plusieurs minutes — Marp ouvre Chrome pour chaque deck. D'où quatre commandes pour viser :

| | Les leçons seules | Les modules seuls |
| --- | --- | --- |
| PDF | `npm run slides:lecons` | `npm run slides:modules` |
| HTML | `npm run slides:lecons:html` | `npm run slides:modules:html` |

Curiosité utile : `slides:modules` lit quand même toutes vos leçons, puisque ce sont elles qui composent les decks de module. Il évite seulement de rendre le deck de chacune. Une leçon corrigée est donc bien reprise dans le PDF de son module, sans avoir à régénérer les dix autres.

## Le PDF résumé d'un module

Le deck d'un module enchaîne les leçons du dossier, dans l'ordre, derrière une slide de titre à son nom. Chaque leçon y est introduite par un intercalaire sur fond plein. Rien n'est réécrit : c'est la suite de ce que vous avez vu leçon après leçon, les leçons verrouillées en moins.

Le site s'en sert : **la dernière leçon de chaque module** affiche un bouton « Télécharger le PDF résumé », à côté de « Marquer comme terminé ». Faites défiler jusqu'en bas de la dernière leçon de ce module, il y est.

Ce bouton n'apparaît **que si le PDF existe** au moment où le site se construit. `npm run build` seul ne le fabrique pas : c'est `npm run slides`, qui réclame Chrome. Plutôt qu'un lien mort, pas de bouton.

## Trois niveaux, le premier trouvé gagne

C'est le point qui prête le plus à confusion. Pour chaque leçon, le générateur cherche de quoi remplir le deck, dans cet ordre :

**Le premier trouvé gagne, et il gagne seul.** Si un fichier `.slides.md` existe, le champ `slidePoints` est purement ignoré — il n'est pas ajouté au deck. Les deux ne se cumulent jamais.

C'est la source d'erreur classique : on enrichit `slidePoints` en se demandant pourquoi le deck ne change pas, alors qu'un fichier `.slides.md` prend le dessus depuis le début.

## La slide de titre est automatique

Ne l'écrivez jamais vous-même. Elle est fabriquée depuis l'en-tête du `.mdx` : `title`, `module` et `cover`.

Elle porte un bandeau sur 30 % de la hauteur, rempli dans cet ordre :

1. l'image `cover:` de la leçon, si elle en a une ;
2. sinon **la couverture de son module** : celle de la première leçon du module qui en déclare une ;
3. sinon l'image par défaut du projet, si vous en configurez une ;
4. sinon un aplat de la couleur principale.

Le deuxième niveau vous évite de répéter `cover:` partout. Illustrez la première leçon d'un module, et tout le module en hérite — ses autres leçons comme la slide de titre de son PDF résumé. Une leçon qui veut sa propre image la déclare, elle l'emporte.

L'image par défaut se règle dans `socle.config.json` :

```json
"slides": { "band": "src/assets/bandeau-slides.png" }
```

## Écrire un `.slides.md`

Le fichier se place **à côté** du `.mdx`, avec le même nom de base :

```
src/content/lecons/module-3/lecon-2.mdx
src/content/lecons/module-3/lecon-2.slides.md   ← le deck
```

Dedans, du Markdown Marp : les slides sont séparées par une ligne de trois tirets. Pas besoin d'en-tête `marp:` ni de thème — le générateur les ajoute.

```markdown
## Ma première slide

- un point
- un autre

---

## Ma deuxième slide

Du texte.
```

N'y remettez pas la slide de titre : elle est déjà là.
