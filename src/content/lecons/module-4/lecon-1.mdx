Pour mettre le template à vos couleurs, un seul fichier à ouvrir.

## La règle

👉 **`socle.config.json`, à la racine du projet.**

```json
{
  "colors": {
    "primary": "#4647AE",
    "text":    "#112E81",
    "page":    "#ffffff"
  },
  "fonts": {
    "heading": "Stack Sans Headline",
    "body":    "Google Sans"
  }
}
```

Trois couleurs, deux polices. Vous enregistrez, vous lancez `npm run dev`, et tout le projet change d'apparence : les liens, les boutons, le liseré des citations, les barres de progression, les intercalaires de vos slides.

## Les couleurs portent leur rôle, pas leur teinte

`primary`, `text`, `page` : ces noms disent à quoi la couleur **sert**, pas de quelle couleur il s'agit. C'est volontaire — une variable appelée `bleuMarine` qui contiendrait du vert après un changement de charte serait un piège. Les polices suivent la même logique : `heading` et `body`.

| | Rôle | Ce qu'elle habille |
| --- | --- | --- |
| `primary` | la couleur principale | liens, boutons, titres de slides, filets |
| `text` | le foncé | le texte, et le survol des boutons |
| `page` | le fond | le fond de page, dont les surfaces sont éclaircies |

Si vous partez d'une palette trouvée sur un site comme Coolors : la plus foncée en `text`, la plus claire en `page`, la plus saturée en `primary`.

## La charte est monochrome, et c'est un choix

Les filets, les traits et les fonds teintés sont tous des **dilutions** de la couleur principale vers le fond de page. Vous ne choisissez aucun ton intermédiaire : ils sont calculés.

| Ton dérivé | Calcul | Sert à |
| --- | --- | --- |
| `primary-soft` | `primary` à 12 % | bandeau d'accueil, leçon courante |
| `surface-muted` | `primary` à 8 % | survols, fonds en creux, code en ligne |
| `border` | `primary` à 30 % | filets des cartes et des tableaux |
| `text-muted` | `text` à 72 % | légendes, métadonnées |

Ce n'est pas une limite du template : le rôle `accent` existe pour accueillir une seconde teinte de marque le jour où il en faudra une. Il ne pointe aujourd'hui que sur `primary`.

## Ce que la commande fait pour vous

`npm run brand` — appelée automatiquement par `dev`, `build` et `slides` — fait trois choses.

**Elle vérifie que votre palette est lisible.** C'est le piège classique du rebranding : une couleur qui rend joliment sur une maquette mais que personne ne peut lire.

```
Couleurs
  ✓ le texte sur le fond de page : 12.13:1
  ✓ la couleur principale sur le fond de page : 7.57:1
```

Ces nombres sont des **rapports de contraste**. La règle d'accessibilité de référence demande au moins 4,5:1 pour du texte courant. En dessous, la commande vous prévient.

**Elle va chercher les polices.** Donnez le nom exact d'une famille Google Fonts : elle vérifie qu'elle existe — et suggère les noms proches si vous vous êtes trompé —, télécharge les fichiers dans `public/fonts/` et écrit les déclarations `@font-face`.

Les polices sont donc **hébergées avec votre site**, pas chargées depuis Google. La page ne dépend de personne pour s'afficher, et aucune donnée de vos apprenants ne part chez un tiers.

**Elle en déduit tous les tons intermédiaires**, selon le tableau ci-dessus.

## Pourquoi ça marche

Parce que rien, dans le reste du projet, n'écrit une valeur en dur. Les composants ne connaissent que des **noms** de variables.

```
socle.config.json ──▶ variables ──▶ tout le reste
                      --color-primary
                      --space-md        composants, mises en page,
                      --text-lg         contenu des leçons, slides…
```

Un composant demande « la couleur principale », pas « ce bleu-là ». C'est ce niveau d'indirection qui rend le rebranding possible — et c'est pour cela qu'il faut résister à la tentation de corriger une couleur directement dans un composant : cela romprait la chaîne, et cette couleur cesserait de suivre la charte.

Deux fichiers de `src/styles/` sont **écrits par la commande** et portent un avertissement en tête : `settings/_brand.scss` et `generic/_fonts.scss`. Les éditer à la main serait sans effet durable.

## Le site et les slides partagent la charte

| Point d'entrée | Habille |
| --- | --- |
| `src/styles/theme.scss` | Le site du cours |
| `src/styles/marp/theme.scss` | Les présentations |

Tous deux partent des **mêmes** fichiers de variables. Modifier un réglage met à jour le site et les slides en même temps — vous n'avez pas de charte à maintenir en double.

Une nuance : le site se rafraîchit tout seul pendant que `npm run dev` tourne, alors que les slides doivent être **régénérées** avec `npm run slides`.

## Les icônes ne sont pas dans la charte

Couleurs et polices se règlent dans `socle.config.json`. Les icônes, non : ce sont des fichiers, dans `public/`.

| Fichier | Où on le voit |
| --- | --- |
| `favicon.svg` | l'onglet du navigateur |
| `favicon.ico`, `favicon-96x96.png` | le même, pour les navigateurs qui ne lisent pas le SVG |
| `apple-touch-icon.png` | l'écran d'accueil d'un iPhone |
| `web-app-manifest-*.png` | le cours installé comme une application |

Pour mettre les vôtres : régénérez le jeu complet — [realfavicongenerator.net](https://realfavicongenerator.net) accepte une image carrée — et remplacez les fichiers **en gardant les mêmes noms**. Rien à changer dans le code.

Une exception : le générateur vous donnera aussi un `site.webmanifest`. **Jetez-le.** Le template produit le sien, avec le nom de votre cours et vos couleurs ; celui du générateur les figerait sur ceux de Socle.
